# PR 审查清单

> 适用于不同语言和框架。仓库自身的 `AGENTS.md`、架构、ADR、Issue/PR 契约和门禁优先于本清单。

## 使用原则

- 先冻结并核对 `baseRefOid`、`headRefOid`，所有行号和结论绑定该 head。
- 先理解声明意图、关联 Issue 和仓库契约，再判断实现。
- 先追踪完整数据流和状态不变量，再做局部代码评论。
- 检查项只是观察角度，不自带严重度；严重度必须由可触发路径、影响和安全网决定。
- 发现必须区分事实、推断与建议。
- 可见结论始终标注 `**身份：Review Agent**`；只有精确当前 head 达到 APPROVE 门禁时使用 `LGTM`。

## Finding 准入与奥卡姆门

Blocking finding 必须同时具备：

1. 明确的 Issue AC、Accepted ADR、仓库不变量或安全/正确性契约锚点。
2. 当前精确 head 的可复现行为或可达代码路径。
3. 可说明的影响。
4. 最小关闭条件。
5. 明确非目标，防止修复自行扩建。

复审先重新调用完整 `$pr-analyze` 工作流并刷新 live head，不得把上一轮分析当作本轮调用的延续。随后建立历史 finding closure ledger、按稳定 invariant ID（不变量编号）归并历史、重跑旧复现，再检查本轮 delta 影响的不变量。复审新增 blocker 必须说明它由新 diff 引入还是此前遗漏、为何上一轮未覆盖，以及为何不能进入 follow-up。

要求新增类型、协议段、表、生成器、canary、原语或层之前，回答：对应哪条 AC、哪个生产消费者读取其值、删除后哪个最终行为会失败、现有机制为何不能表达。答不全则复用或删除。奥卡姆原则是充分方案之间的选择器，不单独构成 blocker。

## 复审熔断

当同一契约锚定不变式再次违反，或处置方声称闭合但当前精确 head 的代码、原复现或实际收集的验证不支持该声明时，完整读取并执行 [circuit-breaker.md](circuit-breaker.md)。

- 区分 `DESIGN_TRIPPED` 与 `EVIDENCE_TRIPPED`；证据未落盘不自动等于设计必须重做。
- 多个输入触发同一个实现缺陷只计一个违反点；不同文件也不自动代表独立根因。以独立可达的 enforcement point、事实所有者和原子/判定边界为证据。
- 熔断判定必须冻结不变式原文、权威 universe 或等价类、enforcement points、排除项和 non-goals。后续不得静默扩大范围。
- 有限、可权威枚举的集合应逐项覆盖；开放或组合爆炸的输入空间使用有依据的等价类、边界和关键交互，不要求无意义全叉乘。
- 熔断提高关闭证据要求，不自动提高 severity，也不把原本可 follow-up 的问题自动变成 blocker。
- `EVIDENCE_TRIPPED` 先重建 exact-head 证据；只有核验确认设计仍不完整时才升级为 `DESIGN_TRIPPED`。
- 每次复审必须显式记录熔断状态与范围审计状态；不能把“未判断”默认为 `NORMAL`。
- 活跃熔断的范围审计为 `INCOMPLETE` 时，只能报告“当前已验证范围”，禁止声称全部关闭、完整覆盖或解除熔断。
- `COMPLETE` 必须指向逐成员或逐等价类的可回读矩阵；“全部检查过”、分类摘要、测试数量或只存在于对话推理中的枚举都不够。
- warning-only 熔断不自动成为 merge gate；是否阻塞必须回到正常可达性、影响、安全网和仓库门禁。

## Pass 1：数据流与 roundtrip

从 diff 识别所有表示变换和持久化边界，例如：

- 对象、JSON、数据库行、协议消息之间的转换
- 外部 API 类型、内部领域模型、UI 模型之间的适配
- 编码、解码、压缩、加密、序列化
- 数据库、文件、缓存、队列或远端服务写入

对每个变换追踪完整路径：

1. 输入从哪里产生，谁负责验证。
2. 经历哪些变换、默认值、过滤和归一化。
3. 在哪里持久化，原子单元是什么。
4. 如何读回、反向变换并提供给消费方。
5. roundtrip 是否保留全部必须字段和语义。

必须检查：

- 写入时存在的字段是否被静默丢弃
- `null`、缺失、空值、默认值是否被错误合并
- 时间、时区、精度、枚举、金额和标识符是否可逆
- 读出端是否假设了写入端未保证的不变量
- 旧数据或旧版本生产的数据能否被新代码读取
- 并发读写是否会暴露部分完成的中间状态

## Pass 2：正确性、安全与状态不变量

### 输入与信任边界

- 用户、AI、第三方 API、Webhook、文件和数据库旧数据是否在使用前验证
- 外部 URL 是否防 SSRF，富文本是否防 XSS
- SQL、shell、模板、表达式和路径是否使用安全参数边界
- 文件路径是否防遍历、符号链接和目标替换
- 生成文本是否可能作为 shell 参数、代码或配置再次执行
- 密钥、个人数据和内部错误是否可能进入日志、报告或评论

### 状态与并发

涉及状态、生命周期、调度、并发、缓存、重试、超时或关闭时，完整读取并应用 [invariant-audit.md](invariant-audit.md)。至少建立稳定不变量台账，并按实际机制选择状态出口表、生产者—消费者表、change-impact frontier（变更影响范围）和证据完整性表；几个反例不能替代覆盖表。

- 谁拥有事实，是否出现多个“当前状态”应答源
- 共享状态写入是否要求所有权、代次、租约或等价凭证
- 凭证校验是否位于串行化临界区内部
- 是否存在 check-then-write 竞态
- 状态转换和持久化是否处于同一原子边界
- 重试、超时、取消和重复投递是否幂等
- 查无记录是否被错误解释成终态或死亡
- 旧任务、旧回调或旧代次是否可能覆盖新状态
- 锁、事务、文件句柄、连接、goroutine/task 是否可靠释放

### 数据完整性

- 新枚举、状态或联合类型是否覆盖所有生产者和消费者
- `switch`、`match`、白名单、过滤条件、序列化和 UI 映射是否遗漏新值
- 数据库约束、应用验证和 API 契约是否一致
- 迁移与回滚是否保持旧数据可解释
- 批量操作部分失败时，结果是否可辨识、重试和恢复

这部分必须搜索 diff 之外的所有相关消费路径，不能只读改动行。

### 错误处理

- 捕获、降级或重试时是否保留原始动作和错误文本
- fallback 是否会把未知事实伪装成成功或终态
- 循环是否有硬上限和可解释终止条件
- 关键失败是否留下不一致状态或不可恢复资源
- 用户是否能看到足以定位问题的证据

## Pass 3：实现完整性与架构契约

- 实现是否覆盖 PR body、关联 Issue、验收标准和 commit 声明
- 是否存在声明完成但没有代码、迁移、测试或操作路径的部分
- 是否出现与声明无关的范围蔓延
- 模块职责和依赖方向是否符合仓库架构
- 纯逻辑与 I/O 是否在正确边界分离
- 是否复用了已有基础设施，或无依据地引入第二套机制
- 抽象是否有真实的第二个使用方，而非预测性设计
- API、事件、命令、配置和持久化格式是否改变了对外契约
- 设计级改动是否具备仓库要求的 ADR、迁移和回滚基线
- 涉及事实所有权、生命周期、原子性、并发、持久化、恢复或跨边界设计时，是否通过 `$impl-gate` 对算法与数据结构的双向追踪
- `VerifiedDesignReceipt` 是否匹配当前 Issue、baseline SHA、实现范围和已接受设计；字段存在、作者自证或 CI 绿色均不等于有效
- 若设计缺失，是否停止实现并进入 design-only 确认轮，而不是由 reviewer 在评论里临时指定架构

## Pass 4：兼容性、性能、测试与运维

### 兼容性

- 请求、响应、导出、命令和配置默认值是否向后兼容
- 前端路由、交互、样式和可访问性是否退化
- 新依赖是否必要，版本、许可证和供应链风险是否可接受
- 数据结构变化是否包含迁移、回滚、旧数据读取和部署顺序
- 功能开关和默认行为是否支持安全升级

### 性能与资源

- 是否存在 N+1、无界循环、无限缓存、全量加载或重复远端调用
- 大数据量和慢依赖下是否有分页、批量、流式、背压与超时
- 资源使用是否与输入规模成合理关系
- 性能问题的严重度是否有真实规模或测量证据支持

### 测试与验证

- 测试是否覆盖真实业务路径，而不是把被测逻辑替换掉
- 正常、边界、异常、并发、重试、迁移和 roundtrip 是否覆盖
- 修复是否有能在修复前失败的回归用例
- 断言是否验证行为结果和不变量，而非仅验证调用次数
- CI 是否绑定当前 head，是否存在 pending、skipped 或 baseline failure
- 本地命令是否实际运行；未运行不能写成通过
- 验收脚本或测试 oracle（判定通过/失败的规则）是否包含真实比较，而非无条件通过
- 是否有负向样例证明 oracle 在违反阈值或不变量时确实失败
- 生成证据是否绑定 exact head、dirty 状态、测量窗口和工具身份，且当前代码与记录一致

### 运维与可恢复性

- 部署顺序、配置、迁移、backfill 和回滚是否可执行
- 部分发布、进程重启、网络分区和依赖失败时是否安全
- 日志、指标和事件是否足以定位失败
- release、deploy、migration 和 production acceptance 是否被错误混为一谈

## Pass 5：对抗性复查

换成攻击者和混沌工程师视角，重点构造：

- 空集合、最大值、重复输入、乱序输入、旧版本输入
- force-push、基线变化和陈旧评论
- 两个并发请求交错在关键读写窗口
- 超时发生在提交前、提交后和响应前
- 成功写入但响应丢失后的重试
- 数据写了一半、迁移跑了一半、批处理部分成功
- 依赖返回格式正确但语义异常的数据
- 错误被捕获、替换或吞掉的路径

同一 agent 完成时必须称为“本地对抗性复查”；只有隔离上下文的 reviewer 才称为“独立审查”。

## 输出前自检

- reviewer 自写的非平凡复现是否已保存到 report-adjacent artifact，并记录 exact head、hash、命令和结果，而不是只留在 `/tmp`
- 决策简报是否只写一次完整 finding；技术附录是否通过 Finding ID 引用而非重复叙述
- `COMPLETE` 是否有逐行 coverage artifact；没有则必须降为 `INCOMPLETE`
- 决策简报里的内部术语是否都当场翻译成人话
- breaker、severity 与 approval decision 是否分别有依据，没有互相自动推导

## 严重度和置信度

### 严重度

| 级别 | 判定标准 | 默认决策影响 |
|---|---|---|
| CRITICAL | 已证明的正常可触发 bug、安全漏洞、数据损坏或无安全网的正确性失败 | 阻塞 approval |
| WARNING | 有意义的异常或运维风险，但影响有限或存在有效安全网 | 通常建议修复 |
| INFORMATIONAL | 可维护性、清晰度或非必要优化 | 不阻塞 |

### 置信度

| 分数 | 证据标准 |
|---|---|
| 9-10 | 已沿精确代码路径验证、复现或有权威运行证据 |
| 7-8 | 代码路径证据强，仅有小范围未验证假设 |
| 5-6 | 合理怀疑但仍需验证，必须明确标注 |
| 1-4 | 通常不进入主报告，除非潜在影响极端 |

发现格式：

```text
[CRITICAL] (confidence: 9/10) path/to/file:42 — 问题描述
  契约锚点: ...
  事实: ...
  复现: ...
  影响: ...
  最小关闭条件: ...
  明确非目标: ...
  建议(不等于架构授权): ...
  复审新增说明: <新 diff 引入 / 此前遗漏及原因 / 首轮不适用>
```

## 不要报告

- diff 已经修复的问题，除非说明独立确认
- 没有行为影响的命名或格式偏好
- “我会换一种写法”式设计偏好
- 没有 Accepted baseline 支持、仅由 reviewer 偏好指定的唯一架构实现
- 只被存在性检查或专门测试消费、删除后最终行为不变的新概念
- 无害的冗余或 no-op
- 没有仓库契约支持的统一行数阈值
- 仅凭猜测得出的性能或安全结论
- 把 CI、review 或 merge 状态问题伪装成代码缺陷
