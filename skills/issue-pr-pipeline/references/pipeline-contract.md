# 流水线契约细节

## 决策包格式（Spec Agent → 人工关口 1）

决策包是一个 Markdown 文件（`work_dir/<issue>/decision-package.md`），遵循 grill 的一次性批量模式：

- 开头一段「范围边界」：Target / In scope / Fixed（issue 与历史评论已定的事实）/ Out of scope / Authority / Done 判据。
- 每个决策一道题，严格用 grill 的格式：`背景 / 举例 / 选项（含可观察后果）/ Recommendation / 你现在只需要决定 / Technical mapping`。
- 每题标档位，**档位只分注意力、不分留痕**（两类题在包内信息量完全一致，禁止折叠【默认过】题）：
  - `【问你】`：agent 倾向某答案但真拿不准（触及钱、身份、状态机、业务语义、跨系统行为，或后果权衡需要业务信息）；答题器会停下来问。
  - `【默认过】`：事实/仓库既有模式充分支持、实现方式选择、可逆、影响局部；必须写明「为什么有把握」；答题器自动采纳推荐，用户可随时推翻。
  - 拿不准标哪档 → 一律【问你】。
- 只收录**frontier 上的题**（其前置事实与决策已定）；依赖未决答案的后续题在末尾「预告」区列出（「若 Q2 答 B，还需确定 Q5」），不提前问。
- **事实不进决策包**：代码、测试、日志、历史 PR 里能查到的一律由 Spec Agent 自己查清并写进契约的「事实基线」，只有真正的用户取舍才成为题目。
- 每题必带 Recommendation 与理由；用户可以只回「全按推荐」。

用户答复写回 `decision-package.answers.md`（编排者原样落盘，格式不限：题号 + 选择/修改意见），随后重跑 `run.sh spec <issue>`（同会话续跑）生成最终契约。

## 实施契约结构（Spec Agent 产出，落到 issue 评论）

```markdown
## 实施契约：<issue 标题>（日期）

### 目标
一段话：改什么、为谁、达成什么可观察变化。

### 事实基线
根因、受影响字段/流程的全部写入与读取路径（逐个 enforcement point）、
不变量、现有测试与既有失败、影响面。全部为 agent 已核实的事实，标注来源（文件:行 / PR / 评论）。

### 决策台账
| # | 决策 | 结论 | 依据（用户答复/推荐采纳） |
每行对应决策包一题；含「预告」题的补答。

### 验收点（可验证）
每条 = 决策 → 可观察行为 → 测试场景。逐条可被自动化测试或明确人工步骤验证。
含回归守护点（不得破坏的既有行为）。

### TDD 场景清单
Coding Agent 必须先写失败测试的场景列表（含边界：空值/回读/并发或日期边界等）。

### 非目标
明确不做什么、不顺手修什么。

### 留给维护者的验收
需要真机/生产/业务复核的点，合并后由维护者执行后关单。
```

## 标签命名空间（扫描器与所有 GitHub 写入统一遵守）

- 流水线产生的标签统一用 `pipeline/` 前缀，一个 issue 同时最多一个：`pipeline/hold`（不适用，原因见评论）、`pipeline/manual`（维护者自行处理，不进入自动交付；由人手动打/摘，扫描器与编排器见此标签一律跳过）、`pipeline/decisions`（待拍板）、`pipeline/ready`（契约就绪，待启动开发）、`pipeline/queued`（开发队列中）、`pipeline/blocked`（中途受阻，需人工解锁，现场快照见评论）、`pipeline/merged`（已合并，待维护者验收后关单）。换状态时扫描器/编排器换标签，不叠加。
- 标签名用 ASCII（供脚本匹配），GitHub 标签描述用中文自报家门（如「流水线：不适用，原因见评论」）。
- 流水线发出的所有 issue 评论统一以 `🤖 流水线自动生成 · 阶段：<spec|review|merge|scan>` 开头，与人工评论一眼可区分。

## 边界情况处置

### 预检关闭（CLOSE_RECOMMENDED）
- `completed`：关联 PR 已合并且逐条对照验收点满足 → 编排者按 gh-issue 协议起草核验评论，经用户确认后 `--reason completed` 关闭。
- `not_planned`：业务已变更、场景不再适用（证据：时间线、替代流程、维护者陈述）→ 同上，`--reason "not planned"`，评论注明「不宣称原问题已修复」。

### 契约缺口兜底（Review 轮发现新歧义）
契约不可能穷尽。Review Agent 发现「契约未覆盖的语义分歧」时：
1. 若契约「决策台账」或 grill 预告区已有可推的默认口径 → Review 按默认口径判，finding 标注 `契约缺口-按默认处理`，编排者在 PR 评论记录，事后可补进契约。
2. 若无默认可推且影响验收 → Review 输出 `WAIT`，编排者把该分歧作为**追加决策题**呈给用户（沿用 grill 单题格式），答后续跑。

### CI 红门归因
Review Agent 必须对每个红 check 做归因：PR 引入 / 基线既有（在 base commit 复跑对照）/ 基础设施（配额、0 步骤失败）/ flaky（本地复跑 + 代码交集判断）。只有全部红门归因于非 PR 因素时，才允许把「带红合并」作为选项呈给用户；归因不明即 WAIT。

### 安全阀与死循环
- `max_rounds`（默认 3）轮内未 APPROVE → 停机报告，保留全部日志与报告供人工接管。
- 若同一 finding 反复未关闭，审查员应判断是否需要 WAIT 和人工介入；脚本不自动比较自然语言 finding。

### 会话与中断恢复
- 三个 agent 各自固定 session id（`mm<issue>-spec/coding/review`），中断后编排者可用同 id 续跑，不丢上下文。
- 日志只追加不删除；阶段产物（决策包/契约/审查报告）都先落盘再进 GitHub。

## 编排者检查单（每阶段转段前）

1. 输出契约机器行存在且合法？
2. 阶段产物落盘（文件存在且非空）？
3. GitHub 侧状态一致（PR/分支/评论确实存在）？
4. 状态文件已更新（PR 号、轮次、verdict）？
5. 若转段将进入人工关口 → 是否已向用户呈现完整材料并取得答复？
